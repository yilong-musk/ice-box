# ice-box Release Process

This document is the reference for every formal release; update it whenever
the process changes.

In short:

```bash
bash scripts/release.sh 0.2.8                              # steps 1-3: bump, gate, captures, PR
# merge the PR, wait for CI on main
gh workflow run release.yml -f tag=v0.2.8 -f mode=release  # steps 4-5: tag, build, publish
```

## Overview

A release is a **`vX.Y.Z` tag on a `main` commit whose CI passed**. The tag is
created either by the `Release` workflow's manual `release` mode or by pushing
it by hand; both run `.github/workflows/release.yml`, which first validates the
tag, version sources, changelog, CI status of the commit, updater key, and
Android keystore in a fast preflight job. It does not re-run the gate: the
required CI checks on `main` already ran it for the same commit. It then builds
the macOS arm64 `.dmg` (plus updater
`.app.tar.gz` / `.sig`), the Windows NSIS `.exe` (plus `.exe.sig`), and one
signed Android `arm64-v8a` APK, and stages everything as a **draft** GitHub
Release. The publish job verifies the assets and updater signatures, writes
`SHA256SUMS`, and only then publishes; publishing makes the release the updater
feed target.
Pre-release tags (`vX.Y.Z-rc.N`) are published as GitHub pre-releases and do
not contain `latest.json`.

macOS releases are ad-hoc signed at the bundle level (documented product
decision: no Developer ID certificate, no notarization). TUN elevation is
documented in [`tun.md`](tun.md#macos-elevation).
First launch still shows an "unidentified developer" Gatekeeper prompt, which
users can override (System Settings → Privacy & Security → Open Anyway on
macOS 15+; right-click → Open on older versions).
CI (`ci.yml` / `release.yml`) asserts the bundle signature with
`scripts/verify-macos-code-sign.sh`, so a signing regression cannot ship.
In-app updates use a separate **minisign** key for integrity; that is not
Developer ID signing.

## Version sources

The version lives in these places and **must stay in sync**:

| File | Key |
|------|-----|
| `Cargo.toml` | `[workspace.package] version` (all crates inherit via `version.workspace = true`) |
| `apps/desktop/package.json` | `"version"` (also displayed in the app UI and GitHub Pages marketing chrome) |
| `apps/mobile/package.json` | `"version"` |
| `apps/mobile/src-tauri/tauri.conf.json` | `bundle.android.versionCode` |

Both `tauri.conf.json` files set `"version": "../package.json"`, so Tauri reads
the installer and app version from the sibling `package.json`. Keep that value:
`bump-version.sh` refuses to run without it, and the preflight resolves the
path and compares the version it points to.

`apps/mobile/src-tauri/gen/android/app/tauri.properties` is generated by
`tauri android build` and ignored by git, so a clean checkout does not contain
it. The bump script writes it; `tauri.conf.json` is the tracked authority for
the Android version code.

`Cargo.lock` is refreshed automatically by `cargo check`.
`scripts/release-preflight.sh` checks every tracked source above before the
release builds start. A local `tauri.properties` is only reported (and ignored)
when it is stale, because a checkout can carry one from an older build; the
Android job verifies the built APK's `versionName` and `versionCode` instead.

The Android version code is `major * 1000000 + minor * 1000 + patch` (the same
integer Tauri uses when `versionCode` is unset). Minor and patch must stay below
1000, otherwise they carry into the next component and collide with a different
release. A pre-release suffix does not change it, so every build of the same
`X.Y.Z` shares one `versionCode`: Android does not treat a later pre-release or
the final build as an upgrade over an earlier one. Testers who installed a
pre-release must uninstall it before installing another build of the same core
version. Desktop clients are unaffected because the updater only follows final
releases. `0.0.0` is rejected. The preflight prints a note when a
`--latest-tag` or `--existing-tag` already uses the same core version; pass
`--fail-on-same-core` to turn that note into an error.

## Updater signing keys (one-time)

In-app updates verify artifacts with minisign; see the
[architecture overview](architecture.md#trust-boundaries) for the trust boundary.
Generate the keypair once (not in the repo):

```bash
cd apps/desktop && npm run tauri signer generate -- -w ~/.tauri/ice-box.key
```

| Material | Where |
|----------|--------|
| Public key | `apps/desktop/src-tauri/tauri.conf.json` → `plugins.updater.pubkey` (committed) |
| Private key | GitHub Actions secret `TAURI_SIGNING_PRIVATE_KEY` |
| Key password | GitHub Actions secret `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` |

Losing the private key means already-installed clients cannot verify a new key;
rotating it abandons those clients (they must reinstall by hand). Back the key
up offline before the first release, together with the password: keep an
encrypted copy in a password manager or on offline media, and verify the
backup by signing a throwaway artifact with it. CI **gate + build** jobs must
**not** set `createUpdaterArtifacts` and do not need these secrets (fork PRs
would otherwise fail). Only `release.yml` merges
`src-tauri/tauri.updater.conf.json` and injects the secrets. The preflight reads
the secret key (decrypting it with the password when needed) and compares its
key id with `plugins.updater.pubkey`, so a wrong key fails before any build.
Before publishing, the publish job also checks that every updater `.sig`
carries the same minisign key id as the committed public key and verifies the
signature cryptographically with `minisign -Vm` against the artifact. A
mismatch or invalid signature fails the release instead of breaking every
installed client.

To rotate the key without abandoning installed clients, first publish a regular
release signed with the **old** key whose binary embeds the **new** public key
in `plugins.updater.pubkey`; clients that install it can then verify releases
signed with the new key. Only after that release reaches users should the CI
secrets switch to the new private key.

## Step-by-step

`scripts/release.sh X.Y.Z` runs steps 1-3 in one go: it starts
`release/vX.Y.Z` from an up-to-date `main`, bumps the version (which also rolls
the changelog), runs a local preflight, `gate-local.sh --full`, and
`capture-docs.sh`, commits only the release files (it stops if anything else
changed), pushes the branch, and opens the PR. `--no-push` stops after the
commit; `--no-changelog` is passed through to the bump. If a step fails before
the commit, it discards its changes, returns to `main`, and deletes the local
branch, so the same command can be run again after the fix. The steps below are
what it does, and how to do them by hand.

### 1. Bump the version

```bash
bash scripts/bump-version.sh 0.1.2
```

The script rewrites every version source above, verifies each pattern was found,
moves the changelog's Unreleased section to the new version (step 2), refreshes
`Cargo.lock` (`cargo check --workspace --quiet`), and prints the release body.
It is all or nothing: when any step fails, every file it wrote (including
`CHANGELOG.md`) is restored, so the same command works again after the fix.
`release.sh`, `bump-version.sh`, `changelog-release.sh`, and the preflight all
validate the version with `scripts/version-lib.sh`, so they accept exactly the
same versions.

### 2. Changelog

Changes are recorded under `## [Unreleased]` in `CHANGELOG.md` (Keep a
Changelog style) as they land. The bump turns that section into
`## [0.1.2] - <today, UTC>` and leaves an empty `## [Unreleased]` above it
(`scripts/changelog-release.sh`). It fails, before the slower bump steps run,
when the Unreleased section is empty, has no `### Added/Changed/Fixed/...`
subsection, or the version already has a section. For a hand-written section
(for example a final release that merges pre-release notes), pass
`--no-changelog`.

The GitHub Release body is deliberately short: `scripts/release-notes.sh` prints
the fixed summary line `Fixes and improvements` and a link to this section in
`CHANGELOG.md`. The full per-release notes stay in the changelog and are never
pasted into the release body. Verify locally before tagging:

```bash
bash scripts/release-notes.sh v0.1.2   # fixed summary + changelog link
```

The script fails when the version's changelog section is missing or empty, so
run it before tagging.

### 3. Gate and merge to `main`

```bash
bash scripts/gate-local.sh --full
bash scripts/capture-docs.sh
```

The release runs the full local gate rather than the scoped default. The gate
does not touch documentation screenshots; `capture-docs.sh` recaptures them when
the version or the UI changed, and screenshots the landing-page showcase for
the README product shot on every run.

The capture scripts write the desktop and phone screenshots plus their version
files to `docs/images/`. Those intermediates are ignored by git; commit only the
composed `docs/images/hero.png` and `docs/images/hero.zh-CN.png`.

Open a PR from a `release/vX.Y.Z` branch and merge into `main` (`release.sh`
opens it for you). `main` has
branch protection: all CI checks (`gate (linux)`, `gate + build (macOS dmg)`,
`gate + build (Windows nsis)`) must pass and one approving review is required.
GitHub does not allow approving your own PR, so a solo maintainer merges with
`gh pr merge --merge --admin` (the repository allows administrator bypass).
`gh pr merge --auto` only queues the merge; auto-merge must be enabled in the
repository settings, and the queued merge still waits for the review.

The release workflow does not repeat the gate. Its preflight runs
`scripts/verify-ci-status.sh`, which requires the newest run of each required
check on the release commit to have completed successfully, so a release is
never built from a tree that only passed the local gate. The required checks
are read from GitHub (the `main` branch protection and any branch ruleset), not
listed in the script, so renaming a CI job only needs the branch protection
updated; with no required checks configured the preflight fails. CI on `main` cancels a
run when a newer commit lands; to release such a commit, re-run its CI first or
release the newer one.

### 4. Tag

Once CI on the merged `main` is green, start the release from the Actions tab
(`Release` → Run workflow → mode `release`) or with:

```bash
gh workflow run release.yml -f tag=v0.1.2 -f mode=release
```

The run validates the current `main` commit, creates the annotated tag
`v0.1.2` on exactly that commit (as `github-actions[bot]`), then builds and
publishes in the same run. A tag pushed with `GITHUB_TOKEN` does not trigger
another workflow run, so nothing runs twice. The tag ruleset must let GitHub
Actions create `v*` tags; see [Repository settings](#repository-settings-one-time).

Pushing the tag by hand still works and starts the same pipeline:

```bash
git tag -a v0.1.2 -m "ice-box v0.1.2"
git push origin v0.1.2
```

The preflight requires the tag commit to be reachable from `main`, CI on it to
have passed, and the version to be newer than every published release and every
existing release tag on `main`. It also validates the updater signing key and
the Android keystore, so it needs the repository secrets. Mode `preflight`
(the default for manual runs) runs only those checks against `main` and does
not tag, build, or publish. Never move or reuse a tag after it has been
created; cut a new patch version instead. Deleting a release does not make its
version reusable.

A pre-release uses the same flow with a suffix, for example
`git tag -a v0.1.2-rc.1 -m "ice-box v0.1.2-rc.1"`. Pre-release tags are
published as GitHub pre-releases, are excluded from `/releases/latest`, and do
not publish `latest.json`, so installed clients never receive them
automatically. Numeric prerelease identifiers must not have leading zeros
(`rc.1`, not `rc.01`). Android `versionCode` is unchanged by the suffix, so all
builds of the same `X.Y.Z` share it; Android will not offer an in-place upgrade
from one to the next. An Android tester who installed a pre-release must
uninstall it before installing the final build (or another pre-release) of the
same core version. Desktop clients are unaffected.

### 5. Release pipeline

`.github/workflows/release.yml` (`on: push: tags: ["v*"]` and
`workflow_dispatch` with mode `preflight`, `release`, or `rehearse`). Every job
checks out the commit the preflight validated:

| Job | Runner | Work |
|-----|--------|------|
| `preflight` | ubuntu-latest | tag is on `main`, the required CI checks passed on the commit, the `release` environment's deployment rules allow this run's ref (`scripts/verify-release-environment.sh`), every version source matches, changelog section exists, signing secrets are present, the updater key matches the committed pubkey, the Android keystore/alias/passwords validate, and the version is newer than every published release and existing tag |
| `tag` | ubuntu-latest | the one gate the build and publish jobs wait on (skipped in `preflight` mode); in manual `release` mode it also creates and pushes the annotated tag on the validated commit |
| `build-macos` | macos-latest | starts right after the preflight (and tag); `tauri build --config src-tauri/tauri.updater.conf.json` (signing secrets); asserts the binary is arm64, the DMG is `ice-box_<ver>_aarch64.dmg`, and the bundle signature; uploads DMG + `*.app.tar.gz` + `.sig` |
| `build-windows` | windows-latest | in parallel with macOS; NSIS (`npm run build:win -- --config src-tauri/tauri.updater.conf.json`, stacked on `tauri.windows.conf.json`); asserts the `ice-box_<ver>_x64-setup.exe` name and payload; uploads EXE + `.exe.sig` |
| `build-android` | ubuntu-latest | in parallel; signed `arm64-v8a` APK (`scripts/build-android-apk.sh release arm64`) → `scripts/verify-android-apk.sh --release --version <ver>` → upload `ice-box_<ver>_android_arm64.apk` |
| `publish` | ubuntu-latest | `needs` all three build jobs; detects the release state before downloading artifacts (a published rerun is verification-only); builds the short release body; cryptographically verifies the updater signatures with minisign against the committed pubkey; writes `SHA256SUMS`; creates a **draft** release, uploads, compares the draft asset list, then publishes (pre-release when the tag has a suffix) and runs `scripts/verify-release-assets.sh` |

The `publish` job uses the `release` environment. Configure required reviewers
on that environment to make publication wait for a human; see
[Repository settings](#repository-settings-one-time).

### Rehearsal

Changes to the pipeline itself are only exercised by a real release, which is
how the draft-lookup bug fixed after v0.2.7 shipped. Before a release that
follows pipeline changes, run a rehearsal:

```bash
gh workflow run release.yml -f mode=rehearse
```

It builds the version currently on `main` (usually already released, so the
newer-than checks are skipped) with the real signing secrets, stages it as a
draft release named `rehearsal-<run id>-<attempt>`, and runs every `publish`
check: signature verification, `latest.json`, `SHA256SUMS`, the draft upload
and asset-list comparison, and the draft lookups that a rerun relies on. It
never publishes and never creates a tag (a draft's tag only appears on publish),
and it deletes the draft at the end, also when a step failed. If a cancelled
run leaves a `rehearsal-*` draft behind, delete it by hand. The rehearsal waits
for `release` environment approval like a real release.

Published assets:

- `ice-box_<ver>_aarch64.dmg` (macOS Apple Silicon, first-time install)
- `ice-box.app.tar.gz` and `ice-box.app.tar.gz.sig` (macOS updater payload; exact names follow Tauri)
- `ice-box_<ver>_x64-setup.exe` (Windows NSIS, first-time install)
- `ice-box_<ver>_x64-setup.exe.sig` (Windows updater signature)
- `ice-box_<ver>_android_arm64.apk` (Android arm64-v8a, signed with the project keystore)
- `SHA256SUMS` (checksums for every asset in the release)
- `latest.json` (`version`, `notes`, `pub_date`, `platforms.darwin-aarch64` /
  `platforms.windows-x86_64`; each `signature` is the **full `.sig` file text**,
  each `url` is `https://github.com/yilong-musk/ice-box/releases/download/<tag>/<asset>`).
  Final releases only; pre-releases do not include it.
- `LICENSE`, `NOTICE`, `sing-box-LICENSE` (root GPLv3 plus bundled sing-box
  license; the upstream text is copied from `third_party/sing-box/LICENSE`
  because two GitHub Release assets cannot share the name `LICENSE`)

The release is created as a draft first, so a failed asset upload never becomes
`/releases/latest`. Rerunning a failed `publish` job resumes the draft; if the
release was already published, it verifies the existing assets and does not
overwrite them.

### 6. Verify

```bash
gh run list --workflow release.yml --limit 1   # conclusion: success
gh release view v0.1.2 --json assets           # dmg, exe, apk, tar.gz, sigs, SHA256SUMS, latest.json
gh release view v0.1.2 --json body             # "Fixes and improvements" + CHANGELOG.md link
bash scripts/verify-release-assets.sh v0.1.2   # asset downloads, SHA-256 checksums, latest.json
```

`verify-release-assets.sh` checks releases produced by this pipeline: it
downloads every asset (with retries), verifies its SHA-256 against
`SHA256SUMS`, rejects extra assets or extra checksum entries, and validates
`latest.json`. Releases published before `SHA256SUMS` was added do not have that
asset and will fail the check.

The release body is the fixed summary plus a changelog link from
`scripts/release-notes.sh`; the link is pinned to the tag, not `main`, so it
keeps pointing at the notes that shipped. The repository URL comes from
`GITHUB_REPOSITORY`, so a fork's release body points at the fork. The full
notes stay one click away in `CHANGELOG.md`.

`latest.json` must list both `darwin-aarch64` and `windows-x86_64` with non-empty
signatures. Fixture coverage: `bash scripts/test-merge-updater-latest.sh`
(also run from `scripts/gate.sh` / `scripts/gate-local.sh`).

The website deploys only after a final release for the current
`apps/desktop/package.json` version is published, and it checks that the
installers the site links to exist. A failed release leaves the site on the
previous version instead of exposing download links that 404.

## Release recovery

| Situation | Action |
|-----------|--------|
| Preflight fails on CI status | Wait for CI on `main` to finish, re-run it if it was cancelled or flaky, and start the release again. |
| Preflight or a build job fails | Fix the cause and re-run the workflow if the tag can stay. A manual `release` run whose tag already exists resumes the tag's commit, even after `main` has moved on, so "Re-run all jobs" or a new `release` dispatch for the same tag both work. If the tag itself is wrong, cut a new patch version; once a release has been published, the version is never reused. |
| `publish` fails before the release is published | Rerun the failed `publish` job. It finds the draft, refreshes the notes, uploads the assets again (removing stale draft assets), and publishes only after the asset list matches. |
| `publish` fails after the release is published | Rerun the job; it detects the published release before downloading artifacts, verifies the existing assets, and does not overwrite them. Fix the cause and cut a new patch if the assets themselves are wrong. |
| The tagged workflow itself is broken | A tag-triggered run uses the workflow from the tag, so a fix on `main` does not change a rerun. If the draft already passed asset verification, publish that verified draft by hand (resolve it with GraphQL or `gh release view`, then `PATCH` it with `draft=false`), run `scripts/verify-release-assets.sh`, and fix the pipeline before the next patch. Do not move the tag. |
| A published release is broken | Cut a higher patch with the fix. Deleting the bad release only makes `/releases/latest` point at the previous version for clients that have not updated yet; Tauri never downgrades, so clients already on the bad version stay there until a higher version exists. |
| A published release was deleted | Do not reuse its version. Deleting a release removes it from the release list but does not make the version legal to publish again; cut a higher patch and rely on tag protection to prevent moving the old tag. |
| A pre-release is broken | Publish another pre-release (`rc.2`, ...). Desktop clients are unaffected (pre-releases are not in `/releases/latest`). Android testers must uninstall the broken build first, because all builds of the same `X.Y.Z` share one `versionCode`. |

Do not edit or replace assets on a published release: `latest.json` embeds the
signature and URL of each updater payload, and clients may already be
downloading it. Forward-fix instead.

## Repository settings (one-time)

These settings are not stored in the repository; configure them once in
GitHub:

- **Release environment**: `Settings → Environments → release`. Add required
  reviewers so `publish` waits for a human after the builds pass. If you add
  deployment branch/tag rules, allow both the `v*` tag pattern and `main` (or
  leave the rules off): tag pushes run on the tag ref, manual `release` and
  `rehearse` runs on `main`. The preflight checks these rules against the
  run's ref and fails before the builds if `publish` would be rejected. The workflow
  serializes releases in the `release` concurrency group, so a run that is
  waiting for approval keeps the group busy and later tag pushes queue behind
  it; approve or reject promptly, or configure an environment wait timer. The
  preflight and build jobs read repository secrets; if you move the signing
  secrets into this environment instead, add `environment: release` to those
  jobs too (each referencing job is approved separately).
- **Tag protection**: create a tag ruleset for `v*` that restricts updates and
  deletions to maintainers. Without it, anyone with write access can push a tag
  that starts the release pipeline. The manual `release` mode creates the tag as
  GitHub Actions, so the ruleset must not restrict creation: on a user-owned
  repository GitHub does not offer the Actions integration as a bypass actor
  (the UI omits it, and the API rejects `Integration 15368` with "Actor GitHub
  Actions integration must be part of the ruleset source or owner
  organization"). Leave `creation` out of the ruleset, or keep pushing tags by
  hand. A signed-tag requirement rules out the manual `release` mode, because
  the workflow's tags are unsigned.
- **Branch protection**: keep the required checks (`gate (linux)`,
  `gate + build (macOS dmg)`, `gate + build (Windows nsis)`) on `main`.
- **Secrets**: set `TAURI_SIGNING_PRIVATE_KEY`,
  `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, `ANDROID_KEYSTORE_BASE64`,
  `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, and
  `ANDROID_KEY_PASSWORD`. The preflight validates the Android keystore,
  store/key passwords, and alias, verifies that the updater key matches
  `plugins.updater.pubkey`, and runs before any build. The updater-key password
  may be empty for an unencrypted key. Back up the updater private key offline;
  see [Updater signing keys](#updater-signing-keys-one-time). Use the manual
  `Release` dry run (step 4) to validate the real secrets before tagging.

The workflow has read-only permissions by default; only the `publish` job can
write to the repository.

## Local vs CI gates

Run `scripts/gate-local.sh` before every commit (it is scoped to the changed
files; use `--full` before a release) and require all CI checks to pass before
merging or tagging, as described above. The maintained reference
for gate coverage, platform splits, and manual live tests is
[`testing.md`](testing.md).

The Rust toolchain is pinned in `rust-toolchain.toml` (CI-3). The workflows
pin the same version for `dtolnay/rust-toolchain`;
`scripts/check-toolchain-pins.sh` (run by both gates) fails when any pin under
`.github/` differs (a `toolchain:` input, quoted or not, a
`dtolnay/rust-toolchain@<version>` ref, or a `rustup` install/default), or when
a `dtolnay/rust-toolchain@stable` step has no `toolchain:` input, so bump them
together. The bundled rule-set
fetches (`scripts/fetch-geoip.sh`) pin a ref per source
(`third_party/loyalsoldier-geoip/REF` for GeoIP,
`third_party/sing-geosite/REF` for GeoSite) and verify SHA-256 against that
source's `CHECKSUMS.sha256` (CI-8); the committed checksum files are the trust
root, as with `third_party/sing-box/CHECKSUMS.sha256`. Both sources are
written to `third_party/bundled-rule-sets/rule-set`, the directory every package
copies from.

## Known issues and workarounds

### Draft releases and the REST by-tag endpoint

`GET /repos/{owner}/{repo}/releases/tags/{tag}` returns 404 for a draft
release, even to a maintainer. `scripts/gh-release-state.sh` and the `publish`
job therefore resolve releases through GraphQL or `gh release view`, which see
drafts. Do not switch them back to the REST by-tag endpoint, or a rerun of a
failed `publish` job will mistake its own draft for a missing release.

### Network instability to github.com

Direct connections to `github.com` from some networks time out intermittently
(HTTP/2 framing errors, port 443 connect failures). Use the local proxy
(`127.0.0.1:17890` on the dev machine) per command:

```bash
git -c http.proxy=http://127.0.0.1:17890 push origin v0.1.2
```

or set it once for the repository:

```bash
git config http.proxy http://127.0.0.1:17890
```

`gh` (the GitHub CLI) is not affected and can be used as a fallback check
during outages. Retry with a short sleep between attempts; connections usually
recover within a minute or two.

## Distribution constraints

The macOS release is ad-hoc signed: Developer ID signing, notarization, and
stapling are not part of the product (documented product decision). TUN
elevation and the helper installation gate exception are maintained in
[`tun.md`](tun.md#macos-elevation). The `.app` inside the published `.dmg`
carries the complete ad-hoc signature, asserted by CI through
`scripts/verify-macos-code-sign.sh`; the DMG container itself is not signed,
which is expected for the ad-hoc identity. First launch still shows an
"unidentified developer" Gatekeeper prompt; users allow it via System
Settings → Privacy & Security → Open Anyway (macOS 15+), right-click → Open
(older versions), or `xattr -dr com.apple.quarantine`.

In-app updates after 0.1.5 do not change that decision: they only check minisign
signatures. Windows NSIS installers remain without Authenticode. Because the
DMG and EXE are not platform-signed, every release also publishes `SHA256SUMS`
so first-time downloaders can verify the files they saved; the updater `.sig`
files cover the in-app update payloads only.

## Android signing (one-time)

Android APKs are signed with one project release keystore. It is not Developer
ID, Play App Signing, or the minisign updater key. The Tauri updater does not
support Android, so the APK is a normal GitHub Release asset and is not listed
in `latest.json`. CI debug APKs are signed with the Android debug key only.

Generate the keystore once, on a machine you control, and keep a copy offline.
Losing it means installed clients must uninstall before they can take a newer
build.

```bash
export ICE_BOX_ANDROID_KEYSTORE_PASSWORD='...'
export ICE_BOX_ANDROID_KEY_PASSWORD='...'
bash scripts/generate-android-keystore.sh "$HOME/.local/share/ice-box/ice-box-release.jks"
```

The script refuses to write the file inside the repository. It uses a JKS
keystore so the store password and the key password stay independent.
`keytool` warns that JKS is a proprietary format; that warning is expected.
Set the GitHub Actions secrets it prints:

| Secret | Value |
|--------|--------|
| `ANDROID_KEYSTORE_BASE64` | base64 of the `.jks` file, one line |
| `ANDROID_KEYSTORE_PASSWORD` | store password |
| `ANDROID_KEY_ALIAS` | `ice-box`, unless you overrode `ICE_BOX_ANDROID_KEY_ALIAS` |
| `ANDROID_KEY_PASSWORD` | key password |

`release.yml` fails the preflight when any of those secrets is empty, before it
spends a build. A local signed build uses the file path instead of the base64
secret:

```bash
export ICE_BOX_ANDROID_KEYSTORE="$HOME/.local/share/ice-box/ice-box-release.jks"
export ICE_BOX_ANDROID_KEYSTORE_PASSWORD='...'
export ICE_BOX_ANDROID_KEY_ALIAS=ice-box
export ICE_BOX_ANDROID_KEY_PASSWORD='...'
bash scripts/build-android-apk.sh release arm64
```

`scripts/verify-android-apk.sh --release --version <ver>` rejects an APK signed
with the Android debug key, an APK that contains any ABI other than
`arm64-v8a`, and an APK whose manifest `versionName` or `versionCode` does not
match the tag. The `x86_64` APK is a local emulator artifact (`debug amd64`) and
is not published.
