# v0.2.3 Development Plan

Status: Release prepared (merge/tag pending)

Branch: `release/v0.2.3`

Last updated: 2026-10-22

This document is the working plan for the next release. It is intentionally
kept outside the user-facing documentation set until the scope is final.

## 1. Scope

### 1.1 Confirmed requirement: node favorites

Users can mark a node as a favorite from the node list. Favorited nodes are
pinned to the top of that list. A favorite belongs to the subscription that
was active when the user created it; switching subscriptions shows only that
subscription's favorites.

### 1.2 Proposed behavior

- Only top-level rows get a star button: strategy-group rows and top-level node
  rows. Rows shown inside an expanded strategy group have no star and cannot be
  favorited there. A tag that is both a top-level row and a group member is
  favorited from its top-level row only.
- Clicking an outlined star favorites the row and pins it above the unfavorited
  rows. The star becomes filled. Clicking it again removes the favorite and the
  row returns to its provider-defined position.
- Favorites are ordered most recently favorited first. Favoriting a node puts
  it at the top; favoriting another node puts the new one above it. Removing a
  favorite and adding it again moves it back to the top. There is no sorting by
  latency or name.
- Favorite writes are single-flight in the UI: while one request is in flight,
  every star is disabled, so a rapid second click cannot race the first write.
- Favorites are available whether the core is running or stopped. Toggling a
  favorite is a UI preference and never regenerates the runtime config, reloads
  the core, or applies the system proxy.
- The star is always visible (there is no hover-only affordance, because the
  same component is used on Android).
- The row is not selectable as a side effect of the star. The button carries
  `aria-pressed` and a localized label/title.
- The feature applies to both node-list surfaces:
  - desktop **Nodes** page;
  - Android **Home** node panel (the same `Nodes` component in embedded mode).
- The desktop tray menu and MCP node order are unchanged. `list_nodes` output
  adds read-only `favorite` and `favorite_rank` fields; both are documented in
  `docs/mcp.md`. No MCP tool other than `list_nodes` changes.

### 1.3 Non-goals

- Cross-device or cloud sync.
- Favorites shared between subscriptions.
- Favoriting individual members inside an expanded strategy group.
- Reordering the tray menu or changing MCP tool behavior beyond the two
  read-only `list_nodes` fields.
- A "Favorites" section header or a separate filtered view.
- Searching, renaming, or grouping favorites.

### 1.4 Decisions

| Topic | Status | Decision |
|---|---|---|
| Favorite granularity | Confirmed | Top-level rows only; expanded group member rows have no star |
| Order among favorites | Confirmed | Most recently favorited first |
| Identity across provider refreshes | Confirmed | Match by node tag; an absent tag is hidden and its pin returns if the same tag reappears |
| Stale tags | Planned | Keep them on disk, but only render tags present in the active profile; cap each subscription at 500 tags and drop the oldest |
| Storage | Planned | Versioned JSON wrapper in the app data root, not webview `localStorage` |
| Store location | Planned | `ice-config`, beside `group-selections.json` and `rules.json`, because favorites are local user preferences |
| Star placement | Planned | `ItemActions`, before Test/Select; embedded phone rows omit the per-row "not running" badge to make room |
| Auto-scroll after pinning | Planned | Do not force a scroll jump; the list reorders in place |
| Concurrency | Planned | Single-flight UI; desktop validation/write under the orchestration lock; mobile under `Mutex<MobileHost>` |
| Snapshot handling | Planned | Do not write the node snapshot from the optimistic toggle; the next refresh writes the backend result |
| Snapshot revision | Planned | Advance the revision only when `selectedTag` changes or the snapshot clears, so content-only changes are not mistaken for a node switch |
| MCP fields | Planned | Expose both `favorite` and `favorite_rank` from `list_nodes` |

## 2. Why backend storage

The frontend could store favorites in `localStorage`, but that would:

- lose them when the webview data is cleared;
- make desktop and Android persistence behave differently;
- duplicate subscription-scope logic in the UI;
- leave no path for the tray or MCP to use the same state later.

A small versioned JSON file in the application data directory is consistent with
`group-selections.json` and `rules.json`, and keeps the data independent of the
normalized subscription profile (which is replaced on every refresh).

## 3. Data model and persistence

### 3.1 File

New file in the app data root:

```text
node-favorites.json
```

Shape:

```json
{
  "version": 1,
  "subscriptions": {
    "0f0a5e1c-5d0d-4e0c-9c55-3f7d9f7b3d21": ["🇯🇵 Tokyo", "Auto"],
    "3c1e9b6a-2a18-4a34-8d31-0d2d1b7c4e55": ["HK-01"]
  }
}
```

- `version` is `1`. Future fields can be added to the wrapper with serde
  defaults; unknown top-level fields are ignored.
- Any other version, including a missing or non-numeric one, is an unsupported
  wrapper: reads return empty instead of parsing it under the current schema,
  and writes fail without touching the file so a downgraded build cannot erase
  newer data.
- The `subscriptions` key is the subscription UUID as a string.
- The value is an ordered list of node tags, **most recently favorited first**.
  Use a `Vec<String>` internally; each tag appears at most once.
- Missing or corrupt files degrade to an empty map, matching
  `load_group_selections`, and log a warning.
- Invalid UUID keys are skipped without discarding the rest of the file.
  Malformed subscription values or non-string tags are skipped individually.
  Parse the wrapper through `serde_json::Value` so one bad entry cannot discard
  the rest.
- Each subscription is capped at 500 tags
  (`MAX_FAVORITES_PER_SUBSCRIPTION`). Loading and adding both deduplicate and
  truncate from the tail, so the newest 500 tags are kept.
- Writes use `write_json_atomic`.
- `save_node_favorites` stays private to the module; the public mutators below
  own the lock and the atomic write.

### 3.2 Lifecycle

- **Add favorite**: remove any existing occurrence of the tag, then insert it at
  index `0` under the active subscription ID. This makes the newly favorited
  tag the most recent. Truncate to `MAX_FAVORITES_PER_SUBSCRIPTION`.
- **Remove favorite**: delete the tag. Remove the subscription key when the list
  becomes empty. Removing a tag that is not present is a no-op.
- **Subscription switch**: nothing to migrate; reads are always scoped by the
  active subscription ID.
- **Subscription update**: keep all stored tags. Stale tags stay on disk and are
  ignored for display until the cap drops the oldest ones.
- **Subscription removal**: immediately after a successful removal, delete that
  subscription's key while the caller still holds its subscription-lifecycle
  lock, before the later apply step. Purge failure is logged and does not fail
  the removal.
- **No active subscription**: reads return an empty set; writes return
  `ConfigEmptyOutbounds` ("no active subscription").
- **Unknown tag**: writes return `ConfigInvalid` ("unknown node tag") after
  validating against the active profile.
- **Corrupt file**: treated as empty; no crash. A later write replaces it with
  the sanitized in-memory map.
- **Duplicates**: deduplicate each list while keeping the first (newest)
  occurrence.
- **Concurrency**: serialize read-modify-write with a module-level mutex in the
  favorites module, so direct store callers cannot lose an update. Atomic
  replacement protects readers from partial files. On desktop, the application
  use case additionally takes the orchestration lock for the
  resolve/validate/write sequence, so a toggle cannot interleave with a
  subscription switch or removal. On mobile, `Mutex<MobileHost>` already
  serializes those commands.

### 3.3 Shared API

Add `AppPaths::node_favorites()` returning
`<app-data-root>/node-favorites.json`.

Place the store in `crates/ice-config/src/favorites.rs`. Favorites are local
preferences like group selections and rule overrides, not subscription parsing
state; this also keeps `ice-subscription` focused on fetch/parse/store. Add the
workspace `uuid` dependency to `ice-config` for the subscription key type.

Public API:

```rust
pub struct NodeFavorites { /* BTreeMap<Uuid, Vec<String>>, newest first */ }

pub const MAX_FAVORITES_PER_SUBSCRIPTION: usize = 500;

pub fn load_node_favorites(path: &Path) -> NodeFavorites;
pub fn set_node_favorite(
    path: &Path,
    subscription: Uuid,
    tag: &str,
    favorite: bool,
) -> Result<(), AppError>;
pub fn remove_subscription_favorites(path: &Path, subscription: Uuid) -> Result<(), AppError>;
```

`NodeFavorites` also exposes `contains(subscription, tag)`,
`favorite_rank(subscription, tag)` (the `Vec` index, `0` = newest), and
`tags(subscription)` for the node-list builders. `favorite` and
`favorite_rank` are always derived from the same lookup so they cannot disagree.

`load_node_favorites` reads the versioned wrapper, parses UUIDs tolerantly,
deduplicates each list, and applies the cap. `set_node_favorite` and
`remove_subscription_favorites` acquire the module mutex before reading and
writing.

## 4. Backend changes

### 4.1 Node DTO

Desktop and mobile currently have separate `NodeInfo` structs. Mirror the new
fields in both:

- `favorite: bool` — whether the tag is in the active subscription's list;
- `favorite_rank: Option<usize>` — the tag's position in that list, where `0`
  is the most recently favorited node and `None` means not favorited.

Set both from one lookup; do not compute them independently.

- Desktop: `apps/desktop/src-tauri/src/application/nodes.rs`.
- Mobile: `apps/mobile/src-tauri/src/host.rs`.

Update the `NodeInfo` test constructors in `tray.rs` and `tray_delay.rs` with the
new fields. `collect_nodes` remains the single source for the desktop node list
and MCP `list_nodes`.

### 4.2 Desktop node list

`collect_nodes` currently loads the active profile and group selections. Extend
it to:

1. Resolve the active subscription ID while loading the same profile/index read.
   Carry the ID on `ProfileCacheEntry` so the ID and profile cannot come from
   different index revisions.
2. Load `node-favorites.json` once.
3. Mark each outbound with `favorite` and `favorite_rank`.

Do not change the returned order. Sorting stays a UI concern so the tray and MCP
keep their existing order.

Add the toggle use case:

```rust
pub struct SetNodeFavoriteRequest {
    pub tag: String,
    pub favorite: bool,
}
```

- Take `lock_orchestrate` for the validation and file write, then release it.
  This serializes the toggle with subscription switches, removals, and applies.
  The critical section is a cached profile read plus one small file write; it
  does not regenerate the config.
- Validate the tag against the active profile (groups included) and capture the
  active subscription ID from the same `ProfileCacheEntry`.
- Do not call `apply_after_subscription_change`, `apply_after_rule_change`,
  `broadcast_state_change`, or any config-generation path.
- Register `set_node_favorite` in the desktop command list.

On successful subscription removal, purge that ID's favorites best-effort
immediately after `ice_engine::remove_subscription` and before
`apply_after_subscription_change`, while the existing orchestration lock is
still held. The MCP `remove_subscription` path uses the same use case, so it
gets the same purge.

### 4.3 Mobile node list

Mirror the desktop behavior, with one important difference:

- Add a helper such as `MobileHost::profile_with_subscription()` returning
  `Option<(Uuid, Arc<NormalizedProfile>)>`, or an equivalent
  `active_subscription_id()` read. `MobileHost::profile()` currently converts
  `NoActiveSubscription` into an empty profile, so it must not be used to decide
  whether a write should return `ConfigEmptyOutbounds`.
- `MobileHost::list_nodes` marks `favorite` and `favorite_rank` from the active
  subscription's set; no active subscription still yields an empty list.
- Add `MobileHost::set_node_favorite(tag, favorite)`: resolve the active
  subscription first (return `ConfigEmptyOutbounds` when absent), validate
  against that profile, then write.
- Add the `set_node_favorite` Tauri command and register it.
- Purge favorites in `MobileHost::remove_subscription` immediately after a
  successful `manager().remove(id)`, before the command's `apply_config`.
- Do not rewrite the tunnel config, reload the tunnel, or notify it for a
  favorite toggle.

Because mobile commands hold `Mutex<MobileHost>`, subscription switches,
removals, and favorite writes are already serialized.

### 5.3 Equality and snapshots

- Compare normalized `favorite` and `favorite_rank` in `nodesEqual` so a
  toggle re-renders locally and the next refresh updates the shared snapshot.
- Change `writeNodesSnapshot` so `nodesSnapshotRevision` advances only when
  `selectedTag` changes or the snapshot is cleared. Content-only changes
  (favorite, `group_now`, member lists, running state) still notify subscribers
  but are not treated as a node switch by `Home`.
- Do not write the snapshot from the optimistic toggle. The next refresh writes
  the backend result. This avoids a rollback path and keeps the snapshot a
  cache of backend state.
- On a successful request, call `refresh()` so the backend result, ranks, and
  snapshot converge immediately. Background polls must not overwrite an
  optimistic favorite; see 5.4.
- On a failed request, restore the previous local array and show the error. Do
  not call `refresh()` from the failure path, because a successful refresh
  clears the error alert; the next scheduled poll reconciles unrelated fields.
  The snapshot was never optimistically modified, so it still holds the last
  backend result.
- Keep the snapshot shape as `NodeInfo[]`; no favorite-specific snapshot field
  is needed. Update the `nodesSnapshotRevision` comment and tests to describe it
  as a selection revision.

### 5.4 Node row UI

In `apps/desktop/src/pages/Nodes.tsx`:

- Add a star button to both the group-row and leaf-row action sets.
- Use `Star` from `lucide-react`; fill it when active (`fill-current`,
  `text-warn`) and leave it outlined otherwise.
- Use `buttonVariants({ variant: "ghost", size: "icon" })` so the star stays a
  36px touch target. `icon-sm` (32px) was too small in practice.
- In embedded mode (phone), omit the per-row `notRunning` badge from group rows.
  The page-level warning already covers the stopped state, and removing the long
  label creates room for the star without shrinking the other controls.
- `aria-pressed={favorite}`, localized `aria-label` and `title`
  (`Favorite node` / `Unfavorite node`).
- Add `onToggleFavorite(node)` and a single-flight guard:
  - Keep `favoriteInFlightRef` set through the post-success refresh: clear it in
    `finally` only after the refresh returns (or the request fails or skips), so
    a second star cannot race the list while it catches up. The ref is the
    guard; React state is only for the disabled UI.
  - Disable every star while the ref is set, and while a Select/Group Select
    write is pending (`selectionPending`, backed by a synchronous
    `selectionInFlightRef`). Also disable Select/Test on all rows and the
    group-member actions while a favorite is pending, so neither action can
    write the optimistic array into the snapshot before the other result is
    known. Do not reuse the existing `busy` state for the star: it also covers
    delay tests, which should not block favorites.
  - Background/state-change refreshes skip while the ref is set; the explicit
    post-success refresh passes `allowDuringFavorite` and runs before the ref
    clears.
- Call `nextGeneration()` before the optimistic update so an in-flight poll
  cannot replace the star with stale data.
- Optimistically apply `applyFavoriteToNodes`, call `api.setNodeFavorite`, then
  `await refresh({ allowDuringFavorite: true })` on success while the ref stays
  set; clear the ref in `finally`. On failure, restore the previous array and
  show an `ErrorAlert`; do not refresh from the failure path, or the alert will
  be cleared.
- Do not write the node snapshot from the optimistic path.
- The star must work while the core is stopped.

Add i18n keys in both dictionaries in `apps/desktop/src/lib/i18n.tsx`, for
example:

- `nodes.favoriteAria`
- `nodes.unfavoriteAria`
- `nodes.favorite` / `nodes.unfavorite` (titles if separate text is needed)

## 6. Edge cases

| Case | Expected behavior |
|---|---|
| Favorite the currently selected node | Row pins to the top and keeps the "In use" marker |
| Favorite a strategy group | Group row pins; its expanded members stay nested and have no stars |
| Favorite another node | The new favorite goes above all earlier favorites |
| Re-favorite after removal | The tag moves back to the top |
| Favorite while scrolled down | List reorders; scroll offset is preserved, no forced jump |
| Rapid double click | Synchronous `favoriteInFlightRef` ignores the second click until the post-success refresh completes |
| Another row action while a favorite is pending | Select/Test and group-member actions are disabled until the favorite write and post-success refresh complete |
| Start Select/Group Select, then click a star | The star is disabled and a synchronous selection ref ignores the click, so the select result cannot write an optimistic favorite into the snapshot |
| Poll lands during a favorite toggle | Background polls are skipped while the favorite write and post-success refresh are in flight; that refresh reconciles |
| Toggle vs subscription switch/removal | Desktop orchestration lock and mobile host mutex serialize them; the toggle validates against the active subscription after the switch/removal and cannot recreate the removed subscription's key |
| Write fails | Local array reverts, the error alert shows the backend message, and the snapshot remains the last backend state |
| Switch subscription | New list shows only the new subscription's favorites |
| Switch back | Previous favorites are still there |
| Subscription refresh | Tags that still exist stay favorited; removed tags are hidden but retained until the cap drops them |
| Subscription removed | Favorites for that ID are purged under the lifecycle lock |
| No active subscription | Star is not rendered because there is no node list; command returns `ConfigEmptyOutbounds` if called |
| Corrupt favorites file | Treated as empty; valid entries survive an invalid key; no crash |
| Invalid UUID key / unknown wrapper field | Invalid subscription keys are skipped; valid entries are retained; unknown fields are ignored |
| More than 500 stale tags | Oldest tags are dropped; the newest favorites remain |
| Core stopped | Star still toggles; no config apply |
| Phone narrow width | Per-row "not running" badge is hidden; the 36px star remains reachable; capture at phone size confirms no overlap |
| Favorite rank missing (legacy/partial data) | The star is filled, the node pins after ranked favorites, and the next refresh supplies the authoritative rank |

   `ice-config`.
